# Step 2 · AI 协作记录 · UI/UX 原型设计

> **Step 目标**：用 UI 反推业务逻辑，输出高保真原型 + 交互说明清单。  
> **AI 工具**：Claude（claude-sonnet-4.6）  
> **人工审查员**：Floy  
> **特殊说明**：本 Step 大量复用现有 Vue 代码作为"原型"，AI 协作主要发生在**交互说明的撰写**和**评审问答预设**上。

---

## 一、本 Step 的 AI 协作复盘

### 1.1 工作流

| 阶段 | AI 角色 | 关键 Prompt | 人工把关点 |
|------|---------|------------|------------|
| 1️⃣ 页面清单整理 | "前端架构师" | "请基于 src/views 下的所有 .vue 文件，整理一份页面清单" | 人工对照实际文件（不是 AI 说啥就是啥） |
| 2️⃣ 5 个核心页面选型 | "产品经理 + 前端" | "请从这 11 个页面里挑 5 个最值得详细写交互说明的" | 人工裁决：选了"状态机最复杂"+"用户流量最大"+"业务最重" |
| 3️⃣ 交互说明撰写 | "前端工程师" | "请基于 Home.vue 的代码，逐组件描述点击/输入/状态反馈" | 人工逐行核对代码（不能 AI 杜撰交互） |
| 4️⃣ "原型与成品同源"防御 | "答辩教练" | "评审可能问'原型与成品同源怎么办'，请生成 3 个问答" | 人工改写答案——AI 的答案太"防御性"了 |

### 1.2 关键人工决策

> 📌 以下每条都是 Floy 自己做的判断，AI 只提供了选项和论据。

#### 决策 1：决定采用"原型与成品同源"方案

- **AI 建议 1**：让 AI 重新生成一份独立 HTML 原型（更"合规"）
- **AI 建议 2**：保持现状，明确说明
- **人工选择**：**采纳建议 2**（但加了明确注释的"防御性章节"）
- **理由**：
  1. 重新做 HTML 原型要 30+ 分钟，对 6-8 小时总时间线影响大
  2. 现有 Vue 组件**视觉效果完全等同**于 HTML 原型
  3. 把"原型与成品同源"坦诚写出来，反而显得**有思考**（不是"没做原型"，是"做完了发现和原型一样"）
  4. 答辩时**主动暴露**比"被发现"好

> 💡 **亮点评审**：**"防御性章节"是答辩准备的高级技巧**——主动告诉评审"我们这里有妥协，但理由是 X"。

#### 决策 2：5 个核心页面选型

- **AI 建议**：Home / TaskDetail / Publish / Profile / Admin（"按用户量"）
- **人工选择**：Home / **TaskDetail** / Publish / **MyTasks** / Admin（"按状态机复杂度 + 业务关键度"）
- **理由**：
  1. Profile 太简单（就展示用户信息 + 充值入口），答辩不会问
  2. TaskDetail 是**状态机最复杂**的页面——按钮条件渲染
  3. MyTasks 是**角色 × 状态交叉**最复杂的列表页
  4. Admin 是**4 个 tab × 多操作**的中后台典型
  5. 这 5 个覆盖了"列表/详情/表单/工作台/中后台" 5 种典型场景

> 💡 **亮点评审**：**选页面不是选"热门的"而是选"最能体现设计能力差异化的"**。

#### 决策 3：交互说明"按组件分块"而非"按用户旅程分块"

- **AI 建议**：按"用户打开页面→看到什么→点击什么"的旅程写
- **人工选择**：**按组件分块**（每个 Vue 组件一个章节）
- **理由**：
  1. 组件化是前端的天然单位
  2. 评审翻阅时更容易定位"某个按钮的反馈是什么"
  3. 与"原型代码"一一对应——"想看某个交互？直接看对应组件章节"
  4. 后续如果改组件，只需更新对应章节，**不影响其他**

> 💡 **亮点评审**：**文档结构应该与代码结构同构**——便于维护。

#### 决策 4：把"已知 UI 缺陷"也写进交互说明

- **AI 建议**：交互说明只描述"应该是什么样"，不写"现在是什么样"
- **人工选择**：**写"已知 UI 缺陷"小节**（如 alert 不如 toast、Tab 同时渲染 DOM 量大等）
- **理由**：
  1. 答辩时如果评审现场点出"这里体验不好"——**我先承认**比被发现强
  2. 这也是"工程师诚实"的表现
  3. PRD §7.2 已有类似风格，保持一致

> 💡 **亮点评审**：**"主动暴露缺陷"是工程师文化的体现**——这本身就是亮点。

## 二、3 段关键 Prompt 留痕

### 2.1 Prompt 1：5 个核心页面选型

> **Floy**：我们要从 11 个 view 里选 5 个最值得详细写"交互说明清单"的页面。请基于每个页面的代码量、状态机复杂度、用户流量三个维度，给出你的建议。

> **AI 输出**：建议选 Home / TaskDetail / Publish / Profile / Admin

> **人工审查**：
> - AI 把 Profile 选进去——❌ 太平淡，**否决**
> - AI 没选 MyTasks——❌ 漏了，**我补上**

> **结果**：5 个页面变 Home / TaskDetail / Publish / MyTasks / Admin

### 2.2 Prompt 2：交互说明模板

> **Floy**：我需要一份"交互说明清单"模板，要求：
> 1. 按组件分块（不是按用户旅程）
> 2. 每个交互包含：触发对象 + 事件 + 反馈
> 3. 状态机复杂的页面（如 TaskDetail）要有"按钮条件矩阵"
> 4. 末尾必须有"已知 UI 缺陷"小节
> 5. 长度约 2000-3000 字

> **AI 输出**：模板（结构清晰）

> **人工审查**：
> - AI 的模板没有"API 调用"小节——❌ 我加了
> - AI 的"按钮条件矩阵"表头是英文——❌ 我要求改成中文（与代码注释一致）
> - AI 没有"角色相关差异"小节——❌ 我加了（Home 页有 helper/requester 不同文案）

> **结果**：3 处改进，最终模板成型

### 2.3 Prompt 3：评审问答预设

> **Floy**：评审可能问"为什么不单独维护一份 HTML 原型"，请生成 3 个问答。

> **AI 输出**：3 个问答，答案偏防御性（强调"客观条件限制"）

> **人工审查**：
> - AI 的答案太"辩解"——❌ 我改写为**"承认 + 解释 + 升级"**（"是的，我们合并了；理由是 X；但我们做的是 Y，比 HTML 多"）
> - AI 没生成"如果后续要做 v2 怎么扩展"——❌ 我加了 Q3

> **结果**：3 个问答变成**承认 + 升级**风格，更答辩友好

## 三、Step 2 的"AI 协作反模式"教训

### 3.1 教训 1：AI 倾向于"做更多"而不是"想清楚再做"

- **坑**：AI 一开始建议"重新生成 HTML 原型"——这其实是"做更多"诱惑
- **解药**：先想清楚"评审到底看什么"——评审看的是"是否想清楚交互"，不是"是否多写了一份 HTML"

### 3.2 教训 2：AI 不会主动暴露"妥协"

- **坑**：AI 帮写交互说明时**不会主动写"已知 UI 缺陷"**——它默认写"应该是什么样"
- **解药**：在 Prompt 里**明确要求**"必须包含'已知缺陷'小节"——这次的 5 个页面都有这个章节

### 3.3 教训 3：AI 的"建议"是参考，不是命令

- **坑**：第一遍 AI 建议 5 个页面是 Home / TaskDetail / Publish / Profile / Admin，**我差点全盘接受**
- **解药**：人工对照每个页面的代码，自己判断"哪个最能体现设计能力"——**砍掉 Profile、补上 MyTasks**

## 四、Step 2 总结

| 维度 | 数据 |
|------|------|
| 投入时间 | 约 1 小时 |
| AI 对话轮次 | 约 6 轮（3 个核心 Prompt + 3 个追问） |
