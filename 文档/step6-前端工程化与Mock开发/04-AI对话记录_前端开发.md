## 一、本 Step 的 AI 协作复盘

### 1.1 工作流

| 阶段 | AI 角色 | 关键 Prompt | 人工把关点 |
|------|---------|------------|------------|
| 1️⃣ 编码规范 SPEC | "前端架构师" | "请基于现有 src/ 代码，逆向推导一份编码规范" | 人工加"已违反清单"和"辩护理由" |
| 2️⃣ Mock 差异审计 | "测试工程师" | "请对比 mock/index.js 和 api/index.js，列出差异" | 人工决定"删除 Mock 而非修复"——**第 2 次"减法思维"** |
| 3️⃣ Axios 拦截器说明 | "前端工程师" | "请解释 request.js 的设计 + 改进方向" | 人工加"为什么不完美也是好事"章节 |

### 1.2 关键人工决策（**3 个"AI 给了建议，人做了相反决定"**）

#### 决策 1：删除 Mock 而非修复 Mock

- **AI 建议**：修复 mock 的 20+ 个路径以匹配真接口
- **人工选择**：**删除 mock/index.js**
- **理由**：
  1. 修复 Mock = 重写 Mock（20+ 路径），工作量 ≈ 重写
  2. 修复后的 Mock 也没人用（main.js 默认 false）
  3. **保留 Mock 是技术债**——未来某天有人误开启，会出诡异 bug
  4. **这是第 2 次"减法思维"**（Step 1 决策 3 也是删除团队组队的占位字段）

> 💡 **亮点评审**：**"加法容易减法难"**——AI 永远在加东西，人工要敢于减。

#### 决策 2：双 Token 头是"演进式兼容"而不是 bug

- **AI 默认判断**："为什么同时设 `token` 和 `Authorization`？这是冗余"
- **人工辩护**：**有意为之**——后端 `AuthInterceptor` 优先读 `token` 头，保留 `Authorization` 是为未来切标准 JWT 留路
- **理由**：
  1. 演进式兼容比"一次到位"更稳
  2. 答辩时可说"我们想清楚了，但选择兼容"

> 💡 **亮点评审**：**"看起来冗余的设计"可能是深思熟虑**——AI 不会主动想到这一点。

#### 决策 3：Axios "不完美"是合理工程

- **AI 默认建议**：补全局 Loading、自动重试、CancelToken、401 自动跳登录、请求缓存
- **人工选择**：**只补 401 自动跳登录**（5 分钟），其他都标"v2 再做"
- **理由**：
  1. **每个"不完美"都有合理性**——不是"做不动"，是"性价比"
  2. 评委问"为什么没 XX"时——有标准答案（"用户场景是校园 WiFi 网络稳定"）
  3. 6-8 小时总时间下，**做 1 件事做到 80% 比做 5 件事做到 50% 强**

> 💡 **亮点评审**：**"承认不完美 + 给出理由"是工程师成熟度**——比假装完美强。

## 三、Step 6 的"AI 协作反模式"教训

### 3.1 教训 1：AI 倾向"加东西"而非"减东西"

- **坑**：AI 建议"修复 Mock 的 20+ 路径"
- **解药**：**先问"修了有人用吗？"**——答案是"没有"，所以删除

### 3.2 教训 2：AI 不理解"演进式兼容"

- **坑**：AI 看到"双 Token 头"就报冗余
- **解药**：**先问"这是 bug 还是设计意图？"**——是设计意图，保留

### 3.3 教训 3：AI 倾向"加完美度"而非"匹配实际"

- **坑**：AI 建议补齐全局 Loading / 重试 / 缓存
- **解药**：**先问"用户的实际场景是什么"**——校园 WiFi 稳定，**用户用不到重试**
