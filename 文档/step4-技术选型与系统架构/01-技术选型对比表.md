## 一、后端框架对比

### 1.1 Spring Boot vs Node.js (Express/Nest) vs Python (FastAPI/Django)

| 维度 | **Spring Boot 3.2（已选）** | NestJS (Node.js) | FastAPI (Python) |
|------|---------------------------|------------------|------------------|
| **性能** | ⭐⭐⭐⭐⭐ JVM | ⭐⭐⭐⭐ V8 | ⭐⭐⭐ 解释型 |
| **类型安全** | ⭐⭐⭐⭐⭐ 静态强类型 | ⭐⭐⭐⭐ TypeScript | ⭐⭐⭐ Pydantic |
| **事务支持** | ⭐⭐⭐⭐⭐ @Transactional 一等公民 | ⭐⭐ 需手动管理 | ⭐⭐⭐ SQLAlchemy |
| **学习曲线** | ⭐⭐ 较陡（IoC/AOP） | ⭐⭐⭐⭐ 较平缓 | ⭐⭐⭐⭐⭐ 最平缓 |
| **生态** | ⭐⭐⭐⭐⭐ Java 生态最全 | ⭐⭐⭐ TS 生态 | ⭐⭐⭐ 偏数据/AI |
| **资金一致性** | ⭐⭐⭐⭐⭐ 强类型 + JTA | ⭐⭐⭐ 弱 | ⭐⭐ 弱 |
| **团队熟悉度** | ⭐⭐⭐ 课程学过 | ⭐⭐⭐ 略懂 | ⭐⭐ 较少 |
| **PPT 提示** | "AI 擅长 Python/JS" | "AI 擅长" | "AI 擅长" |

#### 选型决策

> **采纳 Spring Boot**，理由：
> 1. **课程要求掌握 Java EE**（来自课程大纲）—— 用 Python/Node 反而"跑题"
> 2. **资金事务一致性**是本项目核心难点（PRD §6.1 6 个资金动作）—— Spring `@Transactional` 是最稳的方案
> 3. **乐观锁 / 悲观锁 / 分布式锁**——Java 生态最全
> 4. 团队已学 Spring 全家桶

> ⚠️ **坦白**：如果本项目是 "AI 内容生成" 类的，Python 生态更强；但 "资金 + 状态机" 类项目，**Java 仍是更稳的选择**。

## 二、ORM 框架对比

### 2.1 MyBatis-Plus vs Spring Data JPA vs MyBatis (原生)

| 维度 | **MyBatis-Plus 3.5（已选）** | Spring Data JPA | 原生 MyBatis |
|------|---------------------------|-----------------|--------------|
| **SQL 可控性** | ⭐⭐⭐⭐⭐ 自定义 SQL + Lambda | ⭐⭐ 自动生成（黑盒） | ⭐⭐⭐⭐⭐ 完全自定义 |
| **开发速度** | ⭐⭐⭐⭐ 注解式 + Lambda | ⭐⭐⭐⭐⭐ Repository 接口 | ⭐⭐ 需写 XML |
| **复杂查询** | ⭐⭐⭐⭐ QueryWrapper | ⭐⭐⭐ 难 | ⭐⭐⭐⭐⭐ 自由 |
| **分页** | ⭐⭐⭐⭐⭐ 内置插件 | ⭐⭐⭐⭐ Pageable | ⭐⭐ 手写 |
| **乐观锁** | ⭐⭐⭐⭐⭐ @Version 注解 | ⭐⭐ 需手写 | ⭐⭐ 需手写 |
| **学习曲线** | ⭐⭐⭐⭐ 简单 | ⭐⭐⭐ 较陡（实体关系） | ⭐⭐⭐ 中等 |

#### 选型决策

> **采纳 MyBatis-Plus**，理由：
> 1. **乐观锁是本项目必修**（PRD §6.6 已警示）—— `@Version` 注解开箱即用
> 2. **Lambda QueryWrapper** 让代码可读性高（不写 SQL 字符串）
> 3. 团队对 SQL 熟悉，**不依赖 JPA 的"魔法"**
> 4. MyBatis-Plus 是国内最流行的 Java ORM 之一

> ⚠️ **坦白**：如果团队全是 Spring Boot 老手，可能会选 JPA（更 OO）；但本项目**"看得见 SQL"比"自动生成 SQL"更稳**。

> 💡 **亮点评审**：答辩时如果被问"为什么不用组件库"——"**我们要差异化设计感 + 轻量包体积**"。

## 七、认证方案对比

### 7.1 JWT vs Session vs OAuth 2.0

| 维度 | **JWT（已选）** | Session + Cookie | OAuth 2.0 |
|------|----------------|------------------|-----------|
| **前后端分离** | ⭐⭐⭐⭐⭐ 天然适配 | ⭐⭐ 需 CORS 配合 | ⭐⭐⭐⭐ 适配 |
| **无状态** | ⭐⭐⭐⭐✅ 是 | ❌ 服务端存 session | ⭐⭐⭐⭐ |
| **撤销机制** | ⭐⭐ 难（需黑名单） | ⭐⭐⭐⭐⭐ 直接销毁 | ⭐⭐⭐⭐ |
| **移动端友好** | ⭐⭐⭐⭐⭐ 通用 | ⭐⭐ 需 cookie 容器 | ⭐⭐⭐⭐ |
| **复杂度** | ⭐⭐⭐⭐ 简单 | ⭐⭐⭐⭐⭐ 最简单 | ⭐⭐ 复杂 |

#### 选型决策

> **采纳 JWT**，理由：前后端分离架构下，JWT 是事实标准；24h 短期 + 用户量小，**撤销痛点可接受**。

> 💡 **改进方向**：如果做 v2，可加 **refresh token + 短 access token（5min）+ 撤销黑名单**。

## 十、整体选型哲学

> 📌 **本项目的技术选型核心原则**（贯穿所有 6 个对比）：

1. **课程约束 > 业界流行**：Java + MySQL + Vue 3 是课程默认栈，**不为了"用新"而冒险**
2. **稳定性 > 新潮**：不引入 GraphQL/Rust/Go 等"加分但陌生"的技术
3. **看得见 > 自动化**：选 MyBatis-Plus 而非 JPA，因为**看得见 SQL 才好做并发控制**
4. **官方推荐 > 第三方**：Pinia 替代 Vuex、Tailwind 替代自研 CSS
5. **AI 友好度**：选生态成熟、文档完整、社区活跃的技术，**减少 AI 幻觉**

## 十一、潜在质疑点防御

> 📌 **如果评审质疑"为什么不用 XX 技术"，请参照下表回答**：

| 可能的质疑 | 标准回答 |
|----------|---------|
| 不用 Redis？ | 课程时间紧，单实例 MySQL 够用；如做 v2 可加 Redis 缓存任务列表 |
| 不用 Docker？ | 见 PPT 阶段二要求，本期重点在功能落地，部署教程是 step8 的产出 |
| 不用 Spring Cloud？ | 单服务足够，拆微服务是过度设计 |
| 不用 GraphQL？ | 30 个接口 RESTful 已够清晰，GraphQL 学习成本不值 |
| 不用 TypeScript？ | Vue 3 + JS 已够，加 TS 是锦上添花 |
| 不用 Element Plus？ | 校园平台需要差异化视觉，自研 Tailwind 设计系统 |
| 不用 OAuth 2.0？ | 项目无第三方登录需求，JWT 已够 |
| 不用 ELK？ | 日志量小，console + 文件足够 |
| 不用 K8s？ | 单机部署，Docker Compose 足矣 |
