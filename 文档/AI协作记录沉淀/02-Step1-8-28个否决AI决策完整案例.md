# 28 个"否决 AI 决策"完整案例集

> **来源**：8 个 Step 累计 28 次"AI 给了建议，人做了相反决定"的真实记录。  
> **建立日期**：2026-06-08  
> **使用方式**：答辩时直接引用任一案例作为"个人思考"的证据。

---

## 一、为什么这 28 个案例是 j 章的"灵魂"

> 📌 **核心论点**：j 章不是"我们用了 AI"——是"**我们怎么不被 AI 带跑偏**"。

**这 28 个案例**证明：
1. 我们**不是 AI 代码的搬运工**（AI 协作方法论第 4 条）
2. 我们**有真实的人工审查**（不是事后编的）
3. 我们的**每个决策都有"为什么"**（不是"AI 说的就照做"）
4. 我们的**工程判断力**经过实战检验

## 二、28 个案例完整列表

### Step 1 · 产品定义与 PRD 修订（5 个案例）

#### 案例 1.1：信用分上限 100 → 150

| 维度 | 内容 |
|------|------|
| **场景** | 现有 PRD 写"信用分上限 100"，代码 `Math.min(150, ...)` 实际是 150 |
| **AI 建议** | "改代码对齐 PRD，保持文档权威性" |
| **人工选择** | **改文档对齐代码**，PRD 改为"上限 150" |
| **理由** | 1) 改代码要改 Service+测试 2) 改文档改一个数字 3) 实际业务影响为零 4) PRD 自身也有矛盾（"+5 任务完成、+2 好评"会突破 100） |
| **方法论提炼** | "文档/代码冲突时，选改动成本低的那个"——**第 1 次出现** |

> 💡 **AI 不会主动替你做这个决策**——这是工程判断力。

#### 案例 1.2：校园身份认证 → 完全放弃

| 维度 | 内容 |
|------|------|
| **场景** | PRD 提了"未实名认证用户不可发布或承接任务"，代码无任何 auth 字段 |
| **AI 建议 1** | "在 User 表加 `campus_auth_status` 字段，本期模拟通过" |
| **AI 建议 2** | "在范围界定中明确标本期不做" |
| **人工选择** | **采纳建议 2，连字段都不加** |
| **理由** | 1) 校园认证是业务级问题（谁去对接学校？数据怎么来？） 2) 加字段不难但**评审会问"你校园认证怎么做的"**——答不上来反而减分 3) 诚实标"不做"比假装做了一半强 |
| **方法论提炼** | **PPT AI 协作方法论第 4 条"审核员思维"**——不为 AI 的"看起来更完整"建议买单 |

> 💡 **AI 倾向追求"完整"，但工程上要分清优先级**。

#### 案例 1.3：团队组队功能 → 完全放弃（比 1.2 更彻底）

| 维度 | 内容 |
|------|------|
| **场景** | PRD 提了"团队组队 2-3 人"，但代码无任何 team 字段 |
| **AI 建议** | "保留字段、加占位接口" |
| **人工选择** | **连字段都不加**，标"本期不做" |
| **理由** | 1) 接单方组队会引入"任务分成"逻辑，复杂度翻倍 2) 验收逻辑也要重写（多人怎么确认完成？） 3) **加任何字段都意味着改 schema、改 Service、改前端** 4) **保持代码"无占位"**——占位代码比缺失更糟糕 |
| **方法论提炼** | **抵制"过度设计诱惑"**——AI 特别喜欢画大饼，要勇于说"不" |

> 💡 **"加法容易减法难"**——AI 永远在加东西，人要在合适的时候减。

#### 案例 1.4：乐观锁审查警示保留在 PRD 中（**闭环反馈起点**）

| 维度 | 内容 |
|------|------|
| **场景** | `task` 表有 `version` 字段，但代码用 `updateById` 不带 `WHERE version=?` |
| **AI 建议** | "直接帮修好乐观锁 SQL" |
| **人工选择** | **在 PRD 中标"审查警示"，把修复放到 Step 7** |
| **理由** | 1) Step 1 是文档阶段，**先记下问题**比立刻修复更稳 2) Step 7 是后端实现阶段，统一处理并发问题更合适 3) 这条警示**本身就很有价值**——是给评审看的"我们发现了自己的 bug" |
| **方法论提炼** | **好的 PRD 不仅是规范，也记录"已知问题"**——这是工程师思维，不是产品经理思维 |
| **后续** | ⭐ **闭环到 Step 7 修复**——见 `04-闭环反馈完整故事.md` |

#### 案例 1.5：状态机补充"待审核"状态

| 维度 | 内容 |
|------|------|
| **场景** | 代码里 `audit_status: pending` 字段已存在，但 PRD 未提 |
| **AI 建议** | "保持原 5 个状态" |
| **人工选择** | **加入"待审核"**作为 audit_status 字段对应的状态 |
| **理由** | 1) 代码里字段已存在但 PRD 不解释，**评审可能问"这是干嘛的"** 2) 解释为"管理员预审核"既合理又呼应代码 3) **用 PRD 解释代码中看似冗余的字段**——这叫"反向追溯" |

> 💡 **"反向追溯"是工程师的隐藏技能**——AI 不会主动告诉你某个字段的作用。

### Step 2 · UI/UX 高保真原型设计（4 个案例）

#### 案例 2.1：决定采用"原型与成品同源"方案

| 维度 | 内容 |
|------|------|
| **场景** | 受 1 天时间限制，无独立维护 HTML 原型 |
| **AI 建议 1** | "让 AI 重新生成一份独立 HTML 原型"（更"合规"） |
| **AI 建议 2** | "保持现状，明确说明" |
| **人工选择** | **采纳建议 2**（但加了"防御性章节"） |
| **理由** | 1) 重新做 HTML 原型要 30+ 分钟 2) 现有 Vue 组件**视觉效果完全等同** 3) 把"原型与成品同源"坦诚写出来，反而显得**有思考** 4) **主动暴露**比"被发现"好 |
| **方法论提炼** | **"防御性章节"是答辩准备的高级技巧**——主动告诉评审"我们这里有妥协，但理由是 X" |

#### 案例 2.2：5 个核心页面选型（不是 AI 建议的）

| 维度 | 内容 |
|------|------|
| **场景** | 11 个 view 中选 5 个详细写交互说明 |
| **AI 建议** | Home / TaskDetail / Publish / Profile / Admin（"按用户量"） |
| **人工选择** | Home / **TaskDetail** / Publish / **MyTasks** / Admin（"按状态机复杂度"） |
| **理由** | 1) Profile 太简单（就展示用户信息 + 充值入口） 2) TaskDetail 是**状态机最复杂**的页面 3) MyTasks 是**角色 × 状态交叉**最复杂的列表页 4) 这 5 个覆盖了"列表/详情/表单/工作台/中后台" 5 种典型场景 |
| **方法论提炼** | **选页面不是选"热门的"而是选"最能体现设计能力差异化的"** |

#### 案例 2.3：交互说明"按组件分块"而非"按用户旅程分块"

| 维度 | 内容 |
|------|------|
| **场景** | 5 个核心页面的交互说明组织方式 |
| **AI 建议** | 按"用户打开页面→看到什么→点击什么"的旅程写 |
| **人工选择** | **按组件分块**（每个 Vue 组件一个章节） |
| **理由** | 1) 组件化是前端的天然单位 2) 评审翻阅时更容易定位"某个按钮的反馈是什么" 3) 与"原型代码"一一对应 4) 后续如果改组件，只需更新对应章节，**不影响其他** |
| **方法论提炼** | **文档结构应该与代码结构同构**——便于维护 |

#### 案例 2.4：把"已知 UI 缺陷"也写进交互说明

| 维度 | 内容 |
|------|------|
| **场景** | 交互说明是写"应该是什么样"还是"现在是什么样"？ |
| **AI 建议** | 只描述"应该是什么样"，不写"现在是什么样" |
| **人工选择** | **写"已知 UI 缺陷"小节**（alert 不如 toast、Tab 同时渲染 DOM 量大等） |
| **理由** | 1) 答辩时如果评审现场点出"这里体验不好"——**我先承认**比被发现强 2) 这是"工程师诚实"的表现 3) PRD §7.2 已有类似风格，保持一致 |
| **方法论提炼** | **"主动暴露缺陷"是工程师文化的体现**——这本身就是亮点 |

### Step 3 · API 接口契约设计（4 个案例）

#### 案例 3.1：路径前缀 `/api/v1/` → 保留 `/api/`（**改文档成本低原则**）

| 维度 | 内容 |
|------|------|
| **场景** | 6 个 Controller 用 `/api`，API 文档写 `/api/v1/` |
| **AI 建议** | 改 6 个 Controller 加 v1 路径 |
| **人工选择** | **改文档对齐代码** |
| **理由** | 1) 改 6 个 Controller + 前端所有 API 调用——**几十处改动** 2) 改 1 份文档——**几行字** 3) v1 是未来扩展用的，**本项目不打算有 v2** 4) **第 3 次出现"改文档成本低"原则**——是项目稳定的设计哲学 |
| **方法论提炼** | **"什么时候加版本号"本身是个值得讨论的架构决策**——加得早是过度设计，加得晚要全改路径 |
| **第几次** | **第 3 次**（案例 1.1、1.2、3.1） |

> 💡 **3 次出现同一原则 = 这是项目的稳定哲学**。

#### 案例 3.2：不补齐细分错误码 1001-1005 等

| 维度 | 内容 |
|------|------|
| **场景** | API 文档要求细分错误码（1001 用户名/1002 手机号/1003 密码...） |
| **AI 建议** | 补齐细分错误码（增强 API 可用性） |
| **人工选择** | **不补**，保留通用的 400/401/403/404/409 |
| **理由** | 1) 当前 `BusinessException.conflict("任务已被其他人接单")` 错误信息已清晰 2) 细分错误码需要后端**重写所有 Service 的异常抛出点**——工作量 ≈ Step 7 3) 前端已经做了 `error.response?.data?.message` 兜底 4) **错误码是"理想设计"，不是"必须"** |
| **方法论提炼** | **"理想"和"必须"要分清**——AI 喜欢追求"完整"，但工程上要分清优先级 |

#### 案例 3.3：30 个接口全加 @Tag/@Operation 注解？

| 维度 | 内容 |
|------|------|
| **场景** | Swagger 落地是否要给所有接口加注解 |
| **AI 建议** | 必做，且每个 Controller 都要加 `@Tag` + `@Operation` 注解 |
| **人工选择** | **写完整落地说明 + 配置类 + YAML**，但**不加全注解** |
| **理由** | 1) 落地说明本身有 j 章价值 2) 但**全加注解**要改 6 个 Controller 的所有方法 3) springdoc 即使不加注解也能**自动展示接口** 4) 答辩时**展示 Swagger 截图 + 2-3 个关键 Controller 加了注解**就够 |
| **方法论提炼** | **"60% 的工作 vs 100% 的完美"**——在答辩场景下，前者性价比更高 |

#### 案例 3.4：是否坦白"Swagger 落地无法本地验证"

| 维度 | 内容 |
|------|------|
| **场景** | AI 给完整 Swagger 配置，假设"你会执行 mvn 验证" |
| **AI 默认** | 假设你会执行 |
| **人工选择** | **坦白写"本环境无法直接验证，需要 Floy 本地完成"** |
| **理由** | 1) AI 协作方法论第 5 条"闭环反馈"——**不能假装做完了** 2) 给 Floy 留一个**清晰的 TODO**：截图 + 验证 3) 答辩时如果被问"Swagger 跑起来了吗"——**诚实说"配置已写，截图待补"**比"假装跑通"好 |
| **方法论提炼** | **"主动暴露 TODO"是工程师诚实的体现**——这本身就是亮点 |

### Step 4 · 技术选型与系统架构（3 个案例）

#### 案例 4.1：选型对比加"课程熟悉度"维度

| 维度 | 内容 |
|------|------|
| **场景** | 后端框架选型对比 |
| **AI 默认对比维度** | 性能、学习曲线、生态、文档质量（业界标准 4 维） |
| **人工选择** | **追加"课程熟悉度"和"AI 友好度"**两个维度 |
| **理由** | 1) 本项目是**课程设计**——"课程熟悉度"权重 ≥ 性能 2) 答辩时评委默认你是"学生"——用 Java/MySQL/Vue 是"正常"，用 Rust/Go 会"奇怪" 3) "AI 友好度"决定**AI 能不能正确生成代码**——这是 j 章的核心 |
| **方法论提炼** | **对比维度本身就是一种判断**——AI 给的"标准维度"未必适合当前项目场景 |

#### 案例 4.2：不引入 Redis 和消息队列（"沉默决策"）

| 维度 | 内容 |
|------|------|
| **场景** | 单机部署，单数据库实例，任务量小 |
| **AI 建议** | 建议加 Redis 缓存 + RabbitMQ 异步（"工业级标配"） |
| **人工选择** | **不引入任何中间件** |
| **理由** | 1) 课程时间紧（**第 4 次出现"时间紧"原则**） 2) 单实例 MySQL 性能足够 3) WebSocket 已实现实时通知 4) **不增加运维复杂度** |
| **方法论提炼** | **"工业级"不等于"课程级"**——AI 容易追求"工业级"诱惑 |
| **第几次** | **第 4 次**（案例 1.1、1.3、3.1、4.2） |

#### 案例 4.3：状态机用 if 不用框架

| 维度 | 内容 |
|------|------|
| **场景** | 任务有 6 个状态，需要做合法转换校验 |
| **AI 建议** | 用 Spring State Machine 框架（"更严谨"） |
| **人工选择** | **if 判断 + @Transactional** |
| **理由** | 1) 6 个状态不算多 2) 引入 Spring State Machine 增加学习成本 3) 状态机框架的"严谨"是**为了状态 > 10 个的场景** 4) 答辩被问"为什么不用"——"**6 状态可控，过度设计反而增加 bug 风险**" |

### Step 5 · 数据架构与存储建模（3 个案例）

#### 案例 5.1：发现 AI 误报 2 处（**最重要的反 AI 案例**）

| 维度 | 内容 |
|------|------|
| **场景** | AI 报告 12 个 DDL 问题 |
| **AI 报告（部分）** | 1) "`transaction` 缺 `task_id` 索引"  2) "`account` 缺 UNIQUE 索引" |
| **人工审查** | **2 个都是误报**——实际 schema 中都已建 |
| **否决** | **2 个误报都否决** |
| **理由** | 1) AI 看不到 schema 完整内容，**根据字段名猜测**——必须人工核对 2) 误报一旦进入审计报告，**会误导答辩**——必须立即修正 3) **"AI 给的信息要核对"**——是 j 章的核心方法论 |
| **方法论提炼** | **AI 列的问题里可能有 20% 是误报**——人工审查不是为了"挑刺"，是为了"避免被 AI 误导" |
| **影响** | **这是本项目最关键的"反 AI"案例**——证明我们真的在审查，不是走过场 |

#### 案例 5.2：只加注释，不改 DDL（保守策略）

| 维度 | 内容 |
|------|------|
| **场景** | 基于审计报告生成修订版 schema.sql |
| **AI 建议** | 直接改 schema.sql（加外键、换 TINYINT、加索引） |
| **人工选择** | **只加注释，不改 DDL** |
| **理由** | 1) data.sql 的 5 个测试用户已存在，**改 DDL 可能破坏兼容性** 2) 6-8 小时总时间限制下，**改 DDL 风险大、收益小** 3) **审计报告已经记录了所有问题**——本身就是产出物 4) "不修改"是**经过判断的决策**而非"懒得改" |
| **方法论提炼** | **"主动不改"是答辩亮点**——展示"我们想清楚了，但决定不改" |

#### 案例 5.3：把"无外键约束"作为亮点而非缺陷（**反向辩护**）

| 维度 | 内容 |
|------|------|
| **场景** | schema.sql 全部不建 FK 约束 |
| **AI 默认态度** | 缺外键是 bug，要补 |
| **人工态度** | **故意不加**——参考阿里规约 |
| **理由** | 1) 阿里《Java 开发手册》明确建议"不得使用外键与级联" 2) 性能考虑（外键影响 INSERT/UPDATE 5-10%） 3) 分库分表友好 4) 业务层 Service 已做完整性校验 5) **答辩时主动说"我们参考阿里规约"**——直接亮出工程标准 |
| **方法论提炼** | **"不做什么"是比"做什么"更难的决定**——答辩展示"我们想清楚了为什么不做" |
| **应用** | 主动把"缺陷"转化为"亮点"——j 章最高级的"反败为胜" |

### Step 6 · 前端工程化与 Mock 开发（3 个案例）

#### 案例 6.1：删除 Mock 而非修复 Mock（**减法思维**）

| 维度 | 内容 |
|------|------|
| **场景** | `src/mock/index.js` 与真接口路径不一致（20+ 个） |
| **AI 建议** | 修复 mock 的 20+ 路径以匹配真接口 |
| **人工选择** | **删除整个 mock/index.js** |
| **理由** | 1) 修复 = 重写（20+ 路径） 2) 修复后也没人用（main.js 默认 false） 3) 保留是技术债 4) **第 2 次"减法思维"**（案例 1.3 也是删除） |
| **方法论提炼** | **"加法容易减法难"**——AI 永远在加东西，人要在合适的时候减 |
| **第几次** | **第 2 次**（案例 1.3、6.1） |

#### 案例 6.2：双 Token 头是"演进式兼容"而不是 bug

| 维度 | 内容 |
|------|------|
| **场景** | `request.js` 同时设 `token` 和 `Authorization: Bearer xxx` |
| **AI 默认判断** | "为什么同时设？这是冗余" |
| **人工辩护** | **有意为之**——后端 `AuthInterceptor` 优先读 `token` 头，保留 `Authorization` 是为未来切标准 JWT 留路 |
| **理由** | 1) 演进式兼容比"一次到位"更稳 2) 答辩时可说"我们想清楚了，但选择兼容" |
| **方法论提炼** | **"看起来冗余的设计"可能是深思熟虑**——AI 不会主动想到这一点 |

#### 案例 6.3：Axios "不完美"是合理工程

| 维度 | 内容 |
|------|------|
| **场景** | Axios 拦截器缺全局 Loading、自动重试、CancelToken、401 自动跳登录、请求缓存 |
| **AI 默认建议** | 全部补齐 |
| **人工选择** | **只补 401 自动跳登录**（5 分钟），其他都标"v2 再做" |
| **理由** | 1) **每个"不完美"都有合理性**——不是"做不动"，是"性价比" 2) 评委问"为什么没 XX"时——有标准答案（"用户场景是校园 WiFi 网络稳定"） 3) 6-8 小时总时间下，**做 1 件事做到 80% 比做 5 件事做到 50% 强** |
| **方法论提炼** | **"承认不完美 + 给出理由"是工程师成熟度**——比假装完美强 |
| **第几次** | **第 2 次**（案例 2.4、6.3 都体现"主动暴露不完美"） |

### Step 7 · 后端业务逻辑实现（3 个案例 + 闭环反馈）

#### 案例 7.1：转账顺序——"先改状态后转账"（**AI 顺序反了**）

| 维度 | 内容 |
|------|------|
| **场景** | `completeTask` 验收时，状态更新和资金转账的顺序 |
| **AI 建议** | "先转账，再改状态" |
| **人工选择** | **先改状态，再转账** |
| **理由** | 1) 状态改失败 = 没人竞争，**直接抛 409** 2) 状态改成功 = 拿到锁，**再转账不会双倍** 3) 顺序相反会有"转账了但状态没改"的脏数据 4) **代码顺序体现工程深度** |
| **方法论提炼** | **AI 也会"反模式"——表面合理的方案可能顺序反了**——必须追问"为什么这样" |

> 💡 **这是 j 章最强的"反 AI"案例**——AI 给的方案直接被否决，且否决理由是工程深度。

#### 案例 7.2：测试用例覆盖"业务规则"而非"代码覆盖率"

| 维度 | 内容 |
|------|------|
| **场景** | JUnit 单元测试的覆盖目标 |
| **AI 建议** | 追求高行覆盖率（每行都测到） |
| **人工选择** | **测业务规则**（5星+2分、上限150、下限0、状态机非法转换） |
| **理由** | 1) 行覆盖率 100% 也不保证业务正确 2) 业务规则测试是"真正保护业务"的测试 3) 答辩时**业务规则测试更有说服力** |
| **方法论提炼** | **测试的目的不是"覆盖率"而是"防 bug"**——这是工程哲学 |

#### 案例 7.3：6 个状态变更方法不全修（接受不完美 + 风险分级）

| 维度 | 内容 |
|------|------|
| **场景** | acceptTask/submitTask/completeTask/cancelTask/disputeTask/rateTask 都类似缺乐观锁 |
| **AI 默认建议** | 6 个方法都加乐观锁 |
| **人工选择** | **只修 P0/P1**（accept/complete/transfer/cancel/submit），dispute/rate 接受现状 |
| **理由** | 1) dispute 的状态变更不涉及资金 2) rate 只插表不改 task 状态 3) 全部修要改 6 个 Service 方法，**风险大收益小** 4) **接受不完美 + 给理由** |
| **方法论提炼** | **"哪些不修"比"都修"更体现工程判断**——AI 倾向过度修复 |
| **第几次** | **第 3 次**（案例 2.4、6.3、7.3 都体现"接受不完美"） |

> ⭐ **闭环反馈的"修复阶段"**——见 `04-闭环反馈完整故事.md`。

### Step 8 · 联调测试与收官（3 个案例）

#### 案例 8.1：j 章由人工主笔，AI 仅辅助润色（**AI 协作的红线**）

| 维度 | 内容 |
|------|------|
| **场景** | j 章 5000+ 字让 AI 自动生成 |
| **AI 默认** | 帮写完整的 j 章 |
| **人工选择** | **j 章由 Floy 主笔**，AI 仅润色 |
| **理由** | 1) **j 章是"个人反思"**——AI 写不出真人的反思 2) 验收材料明确"个人反思"是 j 章必含——AI 生成的反思是"伪反思" 3) 答辩时评委可能问"这部分是你写的吗"——必须答"是" 4) **AI 协作方法论第 4 条"审核员思维"**——但**人不能既当运动员又当裁判** |
| **方法论提炼** | **让 AI 写"个人反思"是作弊**——本项目坚守这条红线 |
| **本目录的设立** | **本目录（AI协作记录沉淀）的所有"个人反思"内容均由 Floy 主笔** |

> 💡 **这是本目录存在的根本理由**——证明"反思"是真的。

#### 案例 8.2：演示视频 5 分钟只演示"做得好的"（**取舍**）

| 维度 | 内容 |
|------|------|
| **场景** | 5 分钟演示视频的内容选择 |
| **AI 默认建议** | 把"没做的功能"也讲一下（"本期不做，但 v2 会做"） |
| **人工选择** | **5 分钟只演示 P0 主流程**——不提"没做的" |
| **理由** | 1) 5 分钟已经紧——没时间讲"没做的" 2) 主动说"没做"反而提醒评委"这里有空" 3) **展示自信比展示完整更重要** |
| **方法论提炼** | **"主动暴露不完美"是好**（Step 1-7 多次体现），**"主动暴露没做的"是蠢**——两者边界要看场景 |
| **对比** | 案例 2.4、6.3、7.3 是"主动暴露已做功能的不完美"——OK；案例 8.2 是"主动暴露没做的功能"——NOT OK |

#### 案例 8.3：报告整合的章节配比（重点章节多写）

| 维度 | 内容 |
|------|------|
| **场景** | 7 个 Step 的产出整合成 a-j 章节报告 |
| **AI 默认建议** | 每个章节等量分配（每章 ~5000 字） |
| **人工选择** | **重点章节多写**（a/f/j 各 6000-8000 字，c/d/e/g 各 4000-5000 字） |
| **理由** | 1) a/f/j 是**答辩高频被问**——必须充分 2) c/d/e 是"事实陈述"——不需要长篇大论 3) **配比体现"理解深度"**——评委一眼看出哪些章节是"真懂了" |
| **方法论提炼** | **报告不是"内容越多越好"**——是"重点越透越好" |
