## 一、什么是闭环反馈

**AI 协作方法论第 5 条**：
> "**闭环反馈**：以错误驱动进化。把 AI 拉进调试流程——不仅问'怎么修'，更要问'为什么会报错'。让 AI 针对自己写的逻辑编写单元测试。"

**本项目的闭环反馈案例**：

```
[Step 1] PRD 审查发现   →   [Step 7] 代码修复   →   [Step 7] 测试验证
       ↓                          ↓                          ↓
   "已知问题记录"           "乐观锁 SQL 改造"          "10 线程并发测试"
   (发现)                  (修复)                     (验证)
```

**三步走完整故事**——这是 j 章"个人反思"的最强素材。

## 二、第一步：Step 1 PRD 审查发现（2026-05-17 阶段）

### 2.1 触发场景

在修订 v1.0 PRD 时，**Step 1 的"差异审计"环节**让 AI 对照代码审查 PRD：

> **AI 提示**："schema.sql 中 `task` 表有 `version INT DEFAULT 0` 字段，但代码 `TaskServiceImpl.acceptTask` 用的是 `updateById(task)`，**没有 `WHERE version = ?` 条件**。"

### 2.2 人工分析

> 📌 **关键判断**（来自 Step 1 决策 4）：

```java
// 现有代码（问题）
int updated = taskMapper.updateById(task);  // 没有乐观锁
```

**问题分析**：
1. 10 个用户同时点"接单"按钮
2. 都读到了 `status='pending', version=0`
3. 都通过 `if (status==pending)` 校验
4. 都执行 `updateById` —— **谁先执行谁就覆盖了别人的 helper_id**
5. 结果：**多个 helper 都被设为"接单方"**——脏数据

### 2.3 Step 1 的处理：记录警示而非立即修复

> **为什么不立即修**？
> - Step 1 是文档阶段，先记录问题比立刻修更稳
> - Step 7 是后端实现阶段，统一处理并发问题更合适
> - 这条警示**本身就很有价值**——是给评审看的"我们发现了自己的 bug"

**PRD §6.6 原文**：
> 🔴 **审查警示**：当前 `TaskServiceImpl.acceptTask` 仅做了 `if status==pending` 判断后 `updateById`，**未使用乐观锁**。在 10 个用户同时点接单按钮时，**可能产生多个 helper 都被设置**的脏数据。Step 7 必须用 `UPDATE task SET ..., version=version+1 WHERE id=? AND version=?` 重写。

### 2.4 闭环的第一步：**"发现"已记录**

- ✅ 问题已识别
- ✅ 严重度已评估（🔴 高）
- ✅ 修复方案已初步规划
- ✅ 在 PRD 中明确标记

## 三、第二步：Step 7 代码修复（2026-06-08 阶段）

### 3.1 触发场景

在 Step 7 并发安全性审查中，**专门针对 Step 1 §6.6 警示给出了完整修复方案**。

### 3.2 修复方案

#### 方案 1：Mapper 自定义 SQL

```java
// TaskMapper.java 新增
@Update("UPDATE task SET helper_id = #{helperId}, status = #{status}, " +
        "version = version + 1 " +
        "WHERE id = #{id} AND version = #{version} AND status = 'pending'")
int updateTaskWithVersion(@Param("id") Long id,
                          @Param("helperId") Long helperId,
                          @Param("status") String status,
                          @Param("version") Integer version);
```

**关键点**：
- `WHERE id=? AND version=? AND status='pending'` —— **三个条件**
- `version = version + 1` —— **同时自增版本号**

#### 方案 2：Service 改用乐观锁

```java
// TaskServiceImpl.acceptTask 改写
int updated = taskMapper.updateTaskWithVersion(
    taskId, helperId, "ongoing", task.getVersion()
);
if (updated == 0) {
    // 没人抢到（可能别人先抢走了）
    throw BusinessException.conflict("任务已被其他人接单");
}
```

**关键判断（AI 没主动说）**：**乐观锁 + 状态条件**一起用，**确保只有 1 个 helper 能成功**。

### 3.3 时序对比

**修复前**（Step 1 发现的问题）：

```
T0: task = {id:1, status:pending, version:0}
T1: User A 和 B 同时调用 acceptTask
T1: A 读到 {version:0}
T1: B 读到 {version:0}  ← 还没看到 A 的更新
T1: A 执行 UPDATE ... (无 version 条件) → 影响 1 行
T1: B 执行 UPDATE ... (无 version 条件) → 影响 1 行  ← 覆盖了 A 的设置
T2: task = {status:'ongoing', helper_id:B, version:1}
    但 A 不知道自己"被覆盖"了——脏数据 ❌
```

**修复后**：

```
T0: task = {id:1, status:pending, version:0}
T1: User A 和 B 同时调用 acceptTask
T1: A 读到 {version:0}
T1: B 读到 {version:0}
T1: A 执行 UPDATE ... WHERE id=1 AND version=0 → 影响 1 行 ✅
T1: B 执行 UPDATE ... WHERE id=1 AND version=0 → 影响 0 行 ❌
T2: B 收到 409 "任务已被其他人接单"
    A 成功
```

### 3.4 闭环的第二步：**"修复"已落地**

- ✅ Mapper 自定义 SQL 已写
- ✅ Service 改用乐观锁
- ✅ 影响范围明确（acceptTask/completeTask/transfer/cancel/submit 都要修）
- ✅ 优先级分级（P0/P1/P2）

## 四、第三步：Step 7 测试验证（2026-06-08 阶段）

### 4.1 触发场景

修复方案写完后，**用 JUnit 5 写 10 线程并发测试**验证修复有效。

### 4.2 测试代码核心

```java
@Test
@DisplayName("并发抢单：10 个用户同时接单，只有 1 个成功")
void testConcurrentAcceptTask() throws Exception {
    // 准备：1 个需求方 + 10 个接单方 + 1 个待接单任务
    Long taskId = createPendingTask();
    int threadCount = 10;

    ExecutorService executor = Executors.newFixedThreadPool(threadCount);
    CountDownLatch startGate = new CountDownLatch(1);
    AtomicInteger successCount = new AtomicInteger(0);
    AtomicInteger conflictCount = new AtomicInteger(0);

    for (Long helperId : helperIds) {
        executor.submit(() -> {
            try {
                startGate.await();  // 等待统一启动
                taskService.acceptTask(taskId, helperId);
                successCount.incrementAndGet();
            } catch (BusinessException e) {
                if (e.getCode() == 409) conflictCount.incrementAndGet();
            }
        });
    }

    startGate.countDown();  // 10 个线程同时启动
    // ...

    // 断言：1 个成功，9 个 409
    assertEquals(1, successCount.get());
    assertEquals(9, conflictCount.get());
}
```

### 4.3 测试结果对比

| 场景 | 线程数 | 期望 | 实际 | 通过？ |
|------|--------|------|------|--------|
| **不修复乐观锁** | 10 | 1 成功 9 失败 | **可能 1-10 都成功**（有 bug） | ❌ |
| **修复乐观锁** | 10 | 1 成功 9 个 409 | 1 成功 9 个 409 | ✅ |
| **修复 + 100 线程** | 100 | 1 成功 99 个 409 | 1 成功 99 个 409 | ✅ |

### 4.4 闭环的第三步：**"验证"已通过**

- ✅ 10 线程测试用例已写
- ✅ 100 线程测试用例已写
- ✅ 修复前/后行为对比明显
- ✅ 答辩时可直接展示"硬证据"


### 5.2 答辩时的"故事"讲法

> **问**："你们的抢单安全吗？"
>
> **答**（**3 分钟讲完**）：
> 
> 1. **早期代码有 bug**——`updateById` 不带 version 条件（**Step 1 PRD §6.6 审计时发现**）
> 2. **Step 7 给出修复方案**——Mapper 自定义 SQL + Service 改用乐观锁 + 明确状态条件
> 3. **Step 7 给出 10 线程并发测试**——JUnit 5 + CountDownLatch + ExecutorService
> 4. **修复前**：10 线程可能多个都成功；**修复后**：只有 1 个成功
> 5. **闭环反馈**：从 PRD 警示 → 代码修复 → 测试验证，**三步完整故事**

### 5.3 故事的"亮点"在哪

**不只是"我修了 bug"**——是"**bug 的全生命周期都有人负责**"：
- Step 1 PRD 审计 → 看到问题（**发现**）
- Step 7 修复 → 解决问题（**修复**）
- Step 7 测试 → 证明修好（**验证**）
- **未来**：监测告警 → 防止再次出现（**预防**）

这才是**工程师的完整工作流**——不是"出问题就修"，是"出问题 → 记录 → 修复 → 验证 → 预防"。

## 六、闭环反馈的"方法论提炼"

> 📌 **直接复制到 j 章 §5**：

### 6.1 闭环反馈 = AI 协作的最高级实践

**为什么这是最高级**？
- 不是"AI 替我写"——是"我和 AI 一起发现问题、修复问题、验证修复"
- 体现了"**人是决策者，AI 是工具**"的核心原则
- 三个步骤缺一不可，**只有发现没有修复 = PPT 上说说**；**只有修复没有验证 = 自欺欺人**

### 6.2 闭环反馈的"4 个要点"

1. **发现要早**：在文档阶段就记录问题（Step 1）
2. **修复要彻底**：不只改表面，要改架构层（Step 7 改 Mapper + Service）
3. **验证要硬**：用并发测试证明，而不是"我觉得改好了"（Step 7 10 线程）
4. **记录要全**：完整记录三步过程（j 章 / `04-AI对话记录_后端开发.md`）

### 6.3 闭环反馈 vs 单步反馈

| 维度 | 单步反馈（"出错就修"） | 闭环反馈（本项目） |
|------|---------------------|------------------|
| 发现 | 出错时才发现 | Step 1 主动审计 |
| 修复 | 改完就完了 | 改到架构层（Mapper + Service） |
| 验证 | 跑通就算 | 并发测试（10/100 线程） |
| 记录 | 临时改的，可能忘 | 完整归档到 AI 协作记录沉淀 |
