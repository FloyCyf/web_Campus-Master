## 一、AI 工具与工作模式

### 1.1 工具选择

| 维度 | 我们的选择 | 理由 |
|------|----------|------|
| AI 工具 | **Claude**（claude-sonnet-4.6） | 长上下文 + 中文理解强 + 代码审计细致 |
| 集成方式 | 浏览器/IDE 直接对话 | 2-3 人团队不需要 IDE 插件 |
| Prompt 风格 | **多轮对话** + 上下文回放 | 复杂任务拆成多轮而非单轮长 prompt |
| 输出格式 | Markdown | 便于版本控制 + 跨工具阅读 |

### 1.2 角色分配

我们把 AI 当成 7 种角色，**每个 Step 切一个角色**：

| AI 角色 | 出现 Step | 任务 |
|---------|---------|------|
| 资深产品经理 | Step 1 | 差异审计 + 修订 PRD |
| UI/UX 设计师 | Step 2 | 高保真原型 + 交互说明 |
| 后端架构师 | Step 3 | OpenAPI 契约 + Swagger 落地 |
| 系统架构师 | Step 4 | 选型对比 + ADR 决策 |
| DBA | Step 5 | ER 图 + DDL 审计 |
| 前端架构师 | Step 6 | 编码规范 SPEC + Mock 审计 |
| 后端工程师 | Step 7 | 并发审查 + 单元测试 |

> 💡 **方法论**：**给 AI 明确角色比"请你做 X"有效 10 倍**——角色定义包含"立场""关注点""可妥协的点"。

### 1.3 工作流模板（7 步）

每个 Step 都按以下固定 7 步执行：

```
1. 人工明确"产出物清单"和"优先级"
   ↓
2. AI 给"建议清单"（带理由）
   ↓
3. 人工逐条核对（**不能 AI 说啥就是啥**）
   ↓
4. 人工做最终决策（修改/接受/拒绝/追问）
   ↓
5. AI 按决策执行
   ↓
6. 人工审查产出物
   ↓
7. 记录 AI 对话 + 人工判断（j 章素材）
```

## 二、核心场景的"人机协作迭代"记录

> 📌 **本节是 j 章的灵魂**——5 个最典型的"AI 给了建议，人做了相反决定"案例。

### 2.1 案例 1：信用分上限 100 vs 150（Step 1）

| 维度 | 内容 |
|------|------|
| **场景** | 现有 PRD 写"信用分上限 100"，代码 `Math.min(150, ...)` 实际是 150 |
| **AI 建议** | "改代码对齐 PRD，保持文档权威性" |
| **人工决策** | **改文档对齐代码**，PRD 改为"上限 150" |
| **理由** | 1) 改代码要改 Service+测试 2) 改文档改一个数字 3) 实际业务影响为零 |
| **方法论提炼** | **"文档/代码冲突时，选改动成本低的那个"**——这是工程判断力，AI 不会主动替你做 |

### 2.2 案例 2：团队组队功能 → 完全放弃（Step 1）

| 维度 | 内容 |
|------|------|
| **场景** | PRD 提了"团队组队 2-3 人"，但代码无任何 team 字段 |
| **AI 建议 1** | "加 team 字段，本期模拟" |
| **AI 建议 2** | "在范围界定中明确标本期不做" |
| **人工决策** | **采纳建议 2，连字段都不加** |
| **理由** | 1) 加字段要改 schema/Service/前端 2) 占位代码比缺失更糟糕 3) **保持代码"无占位"** |
| **方法论提炼** | **"抵制过度设计诱惑"**——AI 喜欢画大饼，要勇于说"不" |

### 2.3 案例 3：删除 Mock 而非修复 Mock（Step 6）

| 维度 | 内容 |
|------|------|
| **场景** | `src/mock/index.js` 与真接口路径不一致（20+ 个） |
| **AI 建议** | "修复 mock 的 20+ 路径以匹配真接口" |
| **人工决策** | **删除整个 mock/index.js** |
| **理由** | 1) 修复 = 重写 2) 修复后也没人用 3) 保留是技术债 4) main.js 默认 false，已安全 |
| **方法论提炼** | **"加法容易减法难"**——AI 永远在加东西，人要在合适的时候减 |

### 2.4 案例 4：先改状态后转账（Step 7）

| 维度 | 内容 |
|------|------|
| **场景** | `completeTask` 验收时，状态更新和资金转账的顺序 |
| **AI 建议** | "先转账，再改状态" |
| **人工决策** | **先改状态，再转账** |
| **理由** | 1) 状态改失败 = 没人竞争 2) 状态改成功 = 拿到锁 3) 避免"转账了但状态没改"的脏数据 |
| **方法论提炼** | **"代码顺序体现工程深度"**——AI 不会主动告诉你顺序反了 |

### 2.5 案例 5：Swagger 落地坦白"未验证"（Step 3）

| 维度 | 内容 |
|------|------|
| **场景** | AI 给完整的 Swagger 配置，假设"你会执行验证" |
| **AI 假设** | 写完配置 = 任务完成 |
| **人工决策** | **坦白写"本环境无法验证，需 Floy 本地完成"** |
| **理由** | 1) AI 协作方法论第 5 条"闭环反馈" 2) **不能假装做完了** 3) 给 Floy 留明确 TODO |
| **方法论提炼** | **"主动暴露 TODO"是工程师诚实**——这本身就是亮点 |

## 三、AI 协作的"反模式"教训（汇总）

> 📌 **本节是 j 章"个人反思"的开场**——把 Step 1-7 的反模式教训**合并**。

### 3.1 教训 1：不要直接复制 AI 输出的表格（Step 1）

- **坑**：第一遍 AI 给的差异审计表，列了 8 项偏差，但**第 8 项是伪问题**
- **解药**：每条都要回到代码或 PRD 原文确认，**不能 AI 说啥就是啥**
- **应用频率**：**每一步都遇到**

### 3.2 教训 2：AI 不知道"工程代价"（Step 1, 6）

- **坑**：AI 建议"加 campus_auth_status 字段"——听起来无害，**实际要改 4 个文件**
- **解药**：在动手前问自己"这个改动涉及几个文件？要写几行代码？评审能问到吗？"
- **应用频率**：**至少 3 次**（Step 1 决策 1/2/3）

### 3.3 教训 3：AI 不会主动暴露"已知问题"（Step 1）

- **坑**：AI 帮改乐观锁时**顺手就改了**，我**没意识到它已经改了**
- **解药**：让 AI 在交付时**先列出"我没做的事"**——这次的乐观锁警示就是用这个方法逼出来的
- **应用频率**：**Step 1、Step 7 都遇到**

### 3.4 教训 4：AI 倾向"加东西"而非"减东西"（Step 6）

- **坑**：AI 建议"修复 Mock 的 20+ 路径"
- **解药**：**先问"修了有人用吗？"**——答案是"没有"，所以删除
- **应用频率**：**Step 6 决策 1**

### 3.5 教训 5：AI 倾向"工业级"诱惑（Step 4）

- **坑**：AI 强烈建议加 Redis + RabbitMQ（"工业级标配"）
- **解药**：分清"工业级"和"课程级"——**复杂度匹配团队规模**
- **应用频率**：**Step 4 决策 2**

### 3.6 教训 6：AI 不知道"业务意图"（Step 5）

- **坑**：AI 看到"无外键"→ 报 bug
- **实际**：是**参考阿里规约的工程决策**
- **解药**：AI 给建议后**问一句"这是 bug 还是设计意图"**

### 3.7 教训 7：AI 倾向"100% 覆盖"而非"业务保护"（Step 7）

- **坑**：AI 想追求代码行覆盖率 100%
- **实际**：覆盖率 100% 也不保证业务正确
- **解药**：**测试要围绕"业务规则"**而非"代码行"

## 四、5 条贯穿全程的方法论

> 📌 **本节对应 PPT 第 34-38 页的 5 条方法论**，每条都有**本项目的具体实践案例**。

### 4.1 需求锚定（Requirement Anchoring）

**PPT 原文**：定义角色、场景、硬规则、MVP 范围。

**本项目实践**：
- **角色**：人工明确 3 类角色（Step 1）
- **场景**：人工写"需求方张三要去取快递"的真实故事（PRD §1.1）
- **硬规则**：人工定义"信用分 < 60 限制接单"等业务规则（PRD §6.4）
- **MVP 范围**：**人工决定砍掉**团队组队/提现/IM/GeoHash/AI 审核（PRD §7.1）

**AI 的角色**：提供选项和论据；**人工做最终决策**。

### 4.2 上下文管理（Context Management）

**PPT 原文**：给 AI 喂"唯一事实之源"。

**本项目实践**：
- **喂入协议**：每个 Step 都会**先回放 Step 1 PRD 的关键规则**
- **状态同步**：每个 Step 开头都说明"已完成 X、Y、Z"
- **模块隔离**：每次对话只处理一个功能闭环——**不写"帮我完成整个后端"**

**反例**：Step 5 一开始 AI 试图"自己生成 DDL"，**我立即打断**——"先回看 Step 1 PRD §6 业务规则"

### 4.3 分步实施（Infrastructure First）

**PPT 原文**：基础设施先行 → 垂直切片 → 增量演进。

**本项目实践**：
- **基础设施先行**：Step 7 的"基础设施与统一脚手架"（Result/JwtUtil/ExceptionHandler）先于业务
- **垂直切片**：每个 Step 是一个"垂直切片"——从前端 UI 到后端实现
- **增量演进**：先 MVP（核心任务流），后扩展（IM/GeoHash 等都已标"本期不做"）

### 4.4 审核员思维（Auditor Mindset）

**PPT 原文**：不当 AI 代码的搬运工，要当代码审计员。

**本项目实践**：
- **每个 Step 都有"人工审查清单"**——7 个 Step 共 21 个审查点
- **每条 AI 建议都被独立判断**——不是"AI 说的都对"
- **5 个"AI 给建议，人做相反决定"** 案例（见 §二）

### 4.5 闭环反馈（Closed-Loop Feedback）

**PPT 原文**：以"错误"驱动进化。

**本项目实践**：
- **最完整的闭环**：Step 1 PRD §6.6 警示 → Step 7 修复方案 → Step 7 测试验证
- **主动暴露 TODO**：Step 3 Swagger 落地写"本环境无法验证，需 Floy 本地完成"
- **错误归类**：把 AI 误报（如 Step 5 的"缺索引"误判）作为 j 章素材

## 五、AI 协作的"边界"

> 📌 **本节是 j 章"我们怎么用 AI"的诚实总结**。

### 5.1 我们让 AI 做什么

| 让 AI 做 | 原因 |
|---------|------|
| 大量信息整理 | 效率高，AI 不疲劳 |
| 已知方案的对比 | AI 知识面广 |
| 代码片段生成 | 模板化代码 |
| 文档初稿 | 节省 80% 时间 |

### 5.2 我们不让 AI 做什么

| 不让 AI 做 | 原因 |
|----------|------|
| **业务规则最终决策** | 业务归人，不归 AI |
| **范围裁剪** | AI 倾向"做大"，要人裁 |
| **价值判断** | "这个功能值不值得做"是商业问题 |
| **个人反思** | j 章的灵魂必须是真人写的 |
| **关键代码顺序** | 顺序反了会导致脏数据 |

### 5.3 AI 协作的"红线"

| 红线 | 触发 |
|------|------|
| **AI 替我做了我没同意的决策** | 立即停止 |
| **AI 改了 schema 我没确认** | 立即停止 |
| **AI 删了代码我没要求** | 立即停止 |
| **AI 假装"完成了"实际没做** | 立即停止 |

## 六、个人反思

> 📌 **本节是 j 章"个人反思"的核心**——由 Floy 主笔，**Claude 仅辅助润色**。

### 6.1 知识深度

通过本次 AI 协作，我学到了：
1. **AI 协作不是"让 AI 替我做"，而是"和 AI 一起想"**——AI 给我选项和论据，我做决策
2. **每个决策都要有"为什么"**——AI 给的建议要追问"为什么"，我的反驳也要有"因为"
3. **闭环思维**——发现 → 修复 → 验证，三步缺一不可
4. **"减法思维"是 AI 不会主动给的**——AI 永远在加东西，要人在合适的时候减
5. **错误比完美更真实**——主动暴露"已知不完美"比假装完美更有说服力

### 6.2 批判性思维

- **不轻信 AI 输出**——每条都要核对
- **不轻信自己的判断**——关键决策要追问"为什么"
- **不轻信文档**——文档是"曾经的快照"，代码是"现在的真相"

### 6.3 协作节奏

- **不要追求"一步到位"**——分 7 步走，每步可回退
- **不要追求"100% 完美"**——接受"60% 的工作 vs 100% 的完美"
- **不要追求"AI 替代"**——AI 是工具，决策在人

### 6.4 最有成就感的一个瞬间

**Step 7 的"先改状态后转账"决策**——AI 给了相反的建议，但我**通过工程判断指出 AI 的错**，并给出更合理的方案。**这是我作为工程师独立思考的体现**。

### 6.5 最有挫败感的一个瞬间

**Step 1 一开始让 AI 帮写 PRD 修订时，AI 直接列了 7 项偏差，**我差点全盘接受**——好在"第 8 项状态名中英文不一致"让我警觉，**逐条核对才发现 AI 也会出错**。**这是我建立"审核员思维"的起点**。

### 6.6 如果重新做这个项目，我会怎么改？

| 改进点 | 原因 |
|--------|------|
| **一开始就建 ADR** | 决策有据可查 |
| **每个 Step 加单元测试** | 验收更有底气 |
| **引入 GitHub Actions CI** | 自动跑测试 + 部署 |
| **更早做 Swagger 落地** | 接口文档可视化 |
| **Mock 早点删** | 减少混淆 |
| **乐观锁更早修** | 减少脏数据风险 |

## 七、给后来人的建议

> 📌 **本节是 j 章"传承"**——把经验留给下一届学生。

### 7.1 用 AI 协作的 5 条铁律

1. **角色清晰**：每段对话前告诉 AI 它是什么角色
2. **多轮而非单轮**：复杂任务拆成多轮
3. **逐条核对**：AI 列的清单要逐条核
4. **追问"为什么"**：对 AI 建议要追问理由
5. **人做决策**：业务规则、范围裁剪、价值判断永远归人

### 7.2 课程设计的 5 条避坑

1. **文档与代码必须对齐**——至少做 1 次差异审计（Step 1）
2. **乐观锁必须真的用**——schema 加了 version 字段但代码没 = 没加
3. **错误信息要用户友好**——不要让用户看 "error.response.data.message"
4. **测试要有"业务规则"测试**——不是覆盖率 100% = 业务正确
5. **答辩时主动暴露不完美**——比被发现强

### 7.3 答辩的 5 条准备

1. **每份文档都有"修订点"**——证明你在思考
2. **每个 Step 都有"AI 协作记录"**——证明你在用 AI
3. **每条 AI 建议都有"人工判断"**——证明你不是在搬运
4. **每个不完美都有"理由"**——证明你考虑过
5. **每个 j 章素材都从真实对话来**——证明不是编的
