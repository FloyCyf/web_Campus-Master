# Step 3 · AI 协作记录 · API 契约设计

> **Step 目标**：以差异审计为主，输出 Controller vs 原 API 文档的全面对照表；辅助产出 OpenAPI 3.0 + Swagger 落地说明。  
> **AI 工具**：Claude（claude-sonnet-4.6）  
> **人工审查员**：Floy  
> **本 Step 的特殊性**：**审计表本身比 Swagger 落地更有 j 章价值**——直接展示"AI 给了什么、人查了什么、人否决了什么"。

---

## 一、本 Step 的 AI 协作复盘

### 1.1 工作流

| 阶段 | AI 角色 | 关键 Prompt | 人工把关点 |
|------|---------|------------|------------|
| 1️⃣ 接口列表整理 | "API 审计员" | "请基于 6 个 Controller 的源码，列出全部接口" | 人工对照源码确认（不靠 AI 记忆） |
| 2️⃣ 路径/字段对比 | "审计师" | "请把代码接口与 API 接口文档的 v1.0 逐条对比" | 人工找出 AI 漏掉的（如 `withdraw` 是文档多、代码无） |
| 3️⃣ 全局性问题识别 | "架构师" | "基于以上对比，请识别'全局性问题'" | 人工判断**严重度**（如路径前缀 vs 字段名） |
| 4️⃣ 决策：改文档还是改代码 | "工程顾问" | "对于每个偏差，请给出'改文档 / 改代码'建议 + 理由" | 人工做最终决策（**改文档成本低**这个原则第 3 次出现） |
| 5️⃣ Swagger 落地 | "DevOps" | "请给出 springdoc-openapi 2.3.0 的依赖 + 配置 + 注解示例" | 人工评估"是否能在本环境跑通"——不能，所以**坦白说明** |

### 1.2 关键人工决策（**4 个"AI 给了建议，人做了相反决定"**）

#### 决策 1：路径前缀 `/api/v1/` → 保留 `/api/`

- **AI 建议**：改 6 个 Controller 加 v1 路径
- **人工选择**：**改文档对齐代码**
- **理由**：
  1. 改 6 个 Controller + 前端所有 API 调用——**几十处改动**
  2. 改 1 份文档——**几行字**
  3. v1 是未来扩展用的，**本项目不打算有 v2**
  4. **第 3 次出现"改文档成本低"原则**——是项目稳定的设计哲学

> 💡 **亮点评审**：**"什么时候加版本号"本身是个值得讨论的架构决策**——加得早是过度设计，加得晚要全改路径。

#### 决策 2：要不要做"细分错误码 1001-1005 等"

- **AI 建议**：补齐细分错误码（增强 API 可用性）
- **人工选择**：**不补**，保留通用的 400/401/403/404/409
- **理由**：
  1. 当前 `BusinessException.conflict("任务已被其他人接单")` 错误信息已清晰
  2. 细分错误码需要后端**重写所有 Service 的异常抛出点**——工作量 ≈ Step 7
  3. 前端已经做了 `error.response?.data?.message` 兜底
  4. **错误码是"理想设计"，不是"必须"**——评审不会因为这个扣分

> 💡 **亮点评审**：**"理想"和"必须"要分清**——AI 喜欢追求"完整"，但工程上要分清优先级。

#### 决策 3：Swagger 落地是"必做"还是"装饰"

- **AI 建议**：必做，且每个 Controller 都要加 `@Tag` + `@Operation` 注解
- **人工选择**：**写完整落地说明 + 配置类 + YAML**，但**不加全注解**
- **理由**：
  1. 落地说明本身有 j 章价值（"我们做了哪些工程改进"）
  2. 但**全加注解**要改 6 个 Controller 的所有方法，~30 个接口
  3. springdoc 即使不加注解也能**自动展示接口**（只是缺少 description）
  4. 答辩时**展示 Swagger 截图 + 2-3 个关键 Controller 加了注解**就够

> 💡 **亮点评审**：**"60% 的工作 vs 100% 的完美"**——在答辩场景下，前者性价比更高。

#### 决策 4：是否坦白"Swagger 落地无法本地验证"

- **AI 默认假设**：你会执行 `mvn spring-boot:run` 验证
- **人工选择**：**坦白写"本环境无法直接验证，需要 Floy 本地完成"**
- **理由**：
  1. AI 协作方法论第 5 条"闭环反馈"——**不能假装做完了**
  2. 给 Floy 留一个**清晰的 TODO**：截图 + 验证
  3. 答辩时如果被问"Swagger 跑起来了吗"——**诚实说"配置已写，截图待补"**比"假装跑通"好

> 💡 **亮点评审**：**"主动暴露 TODO"是工程师诚实的体现**——这本身就是亮点。

## 二、3 段关键 Prompt 留痕

### 2.1 Prompt 1：差异审计

> **Floy**：请基于以下 6 个 Controller 的源码 + 原 API 接口文档 v1.0（42KB），做一份差异审计表。**重点关注**：
> 1. 路径差异
> 2. 字段命名差异
> 3. 接口存在性差异
> 4. 错误码体系差异
> 5. 状态码差异

> **AI 输出**：约 30 行差异表

> **人工审查**：
> - AI 漏掉了 `withdraw` 接口（文档有，代码无）——❌ 我补上
> - AI 漏掉了 `frozenAmount` vs `frozenBalance` 字段名差异——❌ 我补上
> - AI 漏掉了 `fromUserId/toUserId` vs `reviewerId/revieweeId` 字段名差异——❌ 我补上

> **结果**：补 3 处，最终 18 条偏差

### 2.2 Prompt 2：识别全局性问题

> **Floy**：基于以上差异，请识别**全局性问题**（不是单个接口的，是系统级问题）。

> **AI 输出**：识别出 2 个——路径前缀、错误码体系

> **人工审查**：
> - AI 把"错误码体系"列全局性——⚠️ 严格说不算全局性，是"未实现"
> - **我修正**：错误码体系归到"严重偏差清单"，路径前缀作为**唯一**全局性问题

> **结果**：1 个全局性问题 + 8 个严重偏差（清晰分层）

### 2.3 Prompt 3：Swagger 落地配置

> **Floy**：请给我 springdoc-openapi 2.3.0 的完整落地步骤，包括：依赖、配置类、注解示例、访问 URL。

> **AI 输出**：完整模板

> **人工审查**：
> - AI 没提 SecurityConfig 放行问题——❌ 我加了交叉引用
> - AI 给的配置类有冗余 import——❌ 简化
> - AI 没提"无法本地验证"——❌ 我加了坦白章节

> **结果**：3 处改进

## 三、Step 3 的"AI 协作反模式"教训

### 3.1 教训 1：AI 容易"装专家"——把"理想设计"当"必须"

- **坑**：AI 强烈建议补齐细分错误码（"这是 API 设计的最佳实践"）
- **解药**：分清"理想设计"和"必须做"——答辩不扣分 = 不必须

### 3.2 教训 2：AI 假设"你会做某事"——但它没问过你

- **坑**：AI 给出 Swagger 完整配置，假设"你会执行 mvn spring-boot:run 验证"
- **解药**：**主动暴露 TODO**——给人工留明确动作清单

### 3.3 教训 3：AI 的"建议"需要你做"严重度"判断

- **坑**：AI 把"路径前缀不一致"和"字段名差异"列在同一严重度
- **解药**：人工**重新分级**——路径前缀是全局性（改 30+ 处），字段名是局部性（改 1-2 处）
